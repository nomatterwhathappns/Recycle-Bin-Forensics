# Reproducible synthetic performance measurements

`tools/benchmark.py` measures scan time, process memory high-water, the additional cost of payload hashing, and optional native GUI operations. It is a developer tool supplied in the source archive. The installed application does not acquire evidence or run benchmarks automatically.

## Run the benchmark

Use Python 3.10 or newer in an installed checkout. No additional runtime packages are required for headless measurements:

```sh
python -m pip install .
python -c "from pathlib import Path; Path('work').mkdir(exist_ok=True)"
python tools/benchmark.py --counts 1000 10000 --repeats 3 --work-dir work --output work/benchmark.json
```

Choose a new output filename for each run. The parent directory and `--work-dir` must already exist. The tool rejects existing output files and redirected path components. Each workload is generated inside an exclusively owned temporary directory and removed after the batch; original evidence is never required. A failed child, timeout, incomplete inventory, or incorrect digest stops the batch without publishing a successful report.

For the larger workload, add `100000` to `--counts`. Each item creates two small files. Filesystem allocation usually exceeds their logical byte sizes, so 100,000 pairs can occupy hundreds of megabytes. Generation and cleanup can take longer than the scan itself on some filesystems.

On a graphical machine with working Tk, add `--gui`:

```sh
python tools/benchmark.py --counts 1000 10000 100000 --repeats 3 --gui --timeout 300 --work-dir work --output work/benchmark-gui.json
```

On a Linux test host with Xvfb installed:

```sh
xvfb-run -a python tools/benchmark.py --counts 1000 10000 --repeats 3 --gui --work-dir work --output work/benchmark-xvfb.json
```

The GUI measurements open actual windows. Run them independently of interactive work or other GUI test batches sharing the display. The default child-process timeout is 300 seconds per measurement; `--timeout` can be changed for a slower host. A missing display or Tk installation fails an explicitly requested GUI measurement.

## Workload and verification

Every item has one `$I` metadata file and one regular `$R` payload. Metadata versions alternate between v1 and v2. Fictitious original paths use a deterministic permutation so a path sort is not measured only on an already ordered view. FILETIMEs are exact integers separated by 100 ns. All payloads are 64 bytes by default; `--payload-bytes` changes that size.

Each measurement checks the expected number of candidates, parsed items, selected records, and timeline events; no errors, warnings, skips, or orphans are expected. It checks payload sizes and, in hashing mode, every digest against independently generated bytes. These checks prevent a fast but incomplete scan from being treated as a performance result. Their elapsed time is excluded from scan timing.

This workload measures many small paired artifacts. It does not represent deeply nested acquisitions, broken metadata, redirected inputs, remote filesystems, large recovered files, or every realistic evidence distribution. Corpus correctness checks and controlled real-Windows validation answer different questions.

## What the JSON means

The report has `schema_version: "1.0"`, `report_kind: "benchmark"`, and `status: "completed"` after all requested measurements pass their result checks. `application_version` identifies the application; `source_commit` and `source_tree_dirty` describe the checkout at the start. Commit source changes before a published measurement whenever possible. `null` provenance values mean Git information was unavailable.

`environment` records Python, operating-system/kernel information, processor model, logical CPU count, and filesystem block size when available. Block size does not identify the storage medium. The tool cannot establish whether the backing disk is SSD, virtual storage, shared network storage, or subject to other workloads.

`workloads` gives actual logical byte counts, format counts, payload size, and generation time. Every entry in `measurements` comes from a fresh Python process; process startup/import time is excluded from the scan timer. The same generated dataset is reused across repeats. Hashing-off runs are followed by hashing-on runs; this order is fixed and documented rather than randomized.

For scan measurements:

| Field | Meaning |
| --- | --- |
| `elapsed_seconds` | Wall time inside `scan()` using `perf_counter`, excluding generation, imports, startup, and result validation |
| `process_cpu_seconds` | Process CPU time consumed during the same scan interval |
| `metadata_per_second` | Expected and verified metadata count divided by elapsed scan time |
| `end_to_end_payload_bytes_per_second` | Logical payload bytes divided by complete scan time in hashing mode; `null` when hashing is off |
| `peak_resident_bytes` | Fresh child process high-water resident memory, including interpreter/imports, report construction, and result validation |
| `memory_method` | Source and unit conversion used for memory, or why it is unavailable |

Peak resident memory is not the incremental cost of the scan and does not include the parent generator or other processes. Linux uses `getrusage().ru_maxrss` in KiB, converted to bytes; macOS reports bytes directly; Windows uses `PeakWorkingSetSize`. Other platforms can report `null` rather than guess units. The tool does not label Python allocation tracking as total RAM.

`summary` groups scans by count and hashing mode, with elapsed minimum/median/maximum, median metadata throughput, and maximum observed process high-water. Keep the raw measurements when publishing a summary so repeat variation remains inspectable.

## GUI timing and heartbeat gaps

Each GUI child constructs the real application at 1000×700, starts the scan through its existing background worker, waits for the completed first page, sorts the full inventory by original path, and changes to the next page when one exists. It checks the complete scan and the expected first-page row count. GUI scanning uses payload hashing off; the headless hash-on measurements quantify hashing separately.

`startup_seconds` is application construction and initial display. `scan_and_first_page.elapsed_seconds` covers starting the scan through the completed report and first-page widget update. Sort and page elapsed values measure the synchronous handler work; later painting is observed by the heartbeat rather than added to these handler durations.

A Tk timer requests callbacks every 10 ms. Each phase records observed callback gaps, their median, p95, maximum, and maximum lateness beyond the requested interval. An additional 30 ms settling period captures a timer delayed by the final handler and is outside the operation's elapsed timer. `max_gap_ms` is the longest observed interval between callbacks; it is not a frame rate or a universal responsiveness guarantee. A long gap can expose blocked UI work, painting costs, worker contention, OS scheduling, or a loaded test host. The report preserves the observation without inventing a pass/fail threshold.

## Interpreting published numbers

No OS cache flush is performed. Generation and repeated reads generally warm filesystem caches, so these results cannot be presented as cold-disk performance. Logical payload throughput includes discovery, metadata parsing, safety checks, timeline construction, and hashing; it is not storage-device bandwidth.

Use at least three repeats for comparative statements. Compare the same application version, payload size, counts, Python/Tk versions, cache method, and storage conditions. A managed cloud host or virtual display is useful for reproducibility but does not predict every Parrot laptop or Windows workstation. Published JSON reports and a short explanation of their tested scope belong alongside release notes.

## Recorded 1.3.0 measurements

These actual measurements used CPython 3.12.14 on Linux x86_64, an AMD EPYC 9V74 host exposing three logical CPUs, and Tk 9.0.4 under a virtual display. Each count used three repeats, generated 64-byte payloads, and generally warm/uncontrolled filesystem caches. [Raw report](results/benchmark-1.3.0.json).

| Metadata records | Median scan, hash off (s) | Median scan, hash on (s) | Highest scan-process RSS (MiB) |
| ---: | ---: | ---: | ---: |
| 1,000 | 0.125 | 0.169 | 22.0 |
| 10,000 | 1.376 | 1.846 | 73.8 |
| 100,000 | 15.885 | 19.421 | 594.8 |

| Metadata records | Median GUI scan + first page (s) | Median sort handler (ms) | Longest observed scan/load heartbeat gap (ms) |
| ---: | ---: | ---: | ---: |
| 1,000 | 0.235 | 3.8 | 43.6 |
| 10,000 | 1.655 | 15.0 | 200.4 |
| 100,000 | 18.682 | 81.2 | 598.1 |

At 100,000 records the engine reached about 595 MiB process RSS and the GUI scan/load phase had an observed callback gap of about 0.60 seconds. Pagination bounds displayed rows, while the complete inventory remains in memory. These results establish a practical large-scope cost; do not describe the interface as continuously responsive at that scale. Partition large investigations into documented scopes where appropriate.

A separate [large-payload report](results/benchmark-large-payload-1.3.0.json) used 100 files of 1 MiB each, three repeats, and no GUI. Median scan time was 0.015 s without hashing and 0.111 s with hashing (about 898 MiB/s logical payload throughput during the complete scan). The generated, cache-warm 100 MiB workload does not measure cold-device bandwidth.

The main report measured clean commit `b0e07d4`; the large-payload report measured clean commit `78df265`. Subsequent changes add validation hardening and documentation/results; the engine and benchmark implementation used for these measurements are unchanged. Both reports record their full source commit and dirty-tree state. Full commit identifiers and workload facts remain available in the raw reports.

These timings exclude JSON/CSV/HTML serialization and export writes. They do not cover damaged-input distributions, slow/network media, concurrent workloads, every Python/Tk version, or large payloads beyond the explicitly recorded workload.
